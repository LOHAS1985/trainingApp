## 2. ローカル開発構成

Docker Composeで次のサービスを起動する。

| Service | 役割 | 開発時の公開範囲 |
| --- | --- | --- |
| `frontend` | React + TypeScriptの開発サーバー | 開発PCのブラウザーからアクセス |
| `backend` | Java Spring Boot API | frontendからComposeネットワーク経由でアクセス |
| `db` | MySQL | Compose内部のみ。必要な場合だけ開発PCへポート公開 |

サービス間通信は専用Composeネットワークを使う。backendのDB接続先はComposeのサービス名`db`とし、コンテナ内から`localhost`でDBへ接続しない。

### 2.1 永続化とヘルスチェック

- MySQLデータ領域にnamed volumeを設定する。
- 通常の停止・再起動でDBデータが残ることを確認する。
- DB healthcheck成功後にbackendを開始する。アプリ起動時も接続再試行または明示的な起動失敗を実装する。
- `docker compose down`と、データを消す`down -v`相当の操作をREADMEで明確に区別する。
- DBポートを公開する場合はlocalhostに限定し、公開環境ではDBポートをインターネットへ公開しない。

### 2.2 設定値

`.env.example`にキー名・用途・ダミー値だけを記載する。実際の`.env`はGit管理対象外とする。

想定する設定例:

- `MYSQL_DATABASE`, `MYSQL_USER`, `MYSQL_PASSWORD`, `MYSQL_ROOT_PASSWORD`
- `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD`
- `APP_SESSION_COOKIE_SECURE`
- `APP_ADMIN_BOOTSTRAP_USERNAME`と初期化時にのみ使う初期資格情報

初期資格情報を通常起動のたびに上書きしない。必須設定が不足した場合は、安全でない既定値で起動せずエラー終了する。

### 2.3 開発者起動手順の目標

リポジトリルートから、依存取得・ビルドを含む単一のComposeコマンドで開発環境を起動できることを目標とする。停止、再起動、DB初期化、マイグレーション適用の手順をREADMEに記載する。実際のサービス名、ポート、コマンドは実装リポジトリ構成確定時に揃える。

## 3. コンテナ・バージョン方針

- Node.js、JDK、MySQLのサポート中バージョンを実装開始時に選定し、Dockerfile/Composeで固定する。
- 再現性のため`latest`タグに依存しない。
- 本番用イメージでは開発依存・不要なビルドツールを含めない。
- DBスキーマはFlyway等で管理し、アプリ起動時の適用方針を一元化する。
- ソースをbind mountする開発設定と、本番のimmutable image設定を混在させない。

## 4. 公開構成候補

| 構成 | 適する条件 | 確認点 |
| --- | --- | --- |
| 静的ホスティング + Java APIホスト + マネージドDB | 無料枠優先、個別にサービスを選びたい | Java実行時間、スリープ、RAM、転送量、永続性、DB接続とバックアップ |
| VM/VPS上でDocker運用 | Composeを学び、MySQLを含めて管理したい | 月額、OS/コンテナ更新、HTTPS、監視、バックアップ、障害復旧を自分で行う |
| マネージドMySQL + APIホスト | DB運用負荷を下げたい | 無料枠の有無、容量、接続数、バックアップ復元、料金超過条件 |

MySQL互換DB候補としてTiDB Cloud Starter等を調査対象にできる。ただしMySQLと全機能・運用挙動が同じとみなさず、SQL互換性とマイグレーションを検証する。無料枠の金額・条件は変更されうるため、サービス契約前に公式価格表・規約を確認し、確認日と担当者を記録する。

## 5. 公開環境の構成要件

- HTTPSを必須とする。
- 可能ならフロントエンドとAPIを同一オリジンで配信し、Cookie/CORS設定を単純化する。
- DBはプライベートネットワークまたはサービス内部接続に限定する。
- Secret StoreへDB資格情報等を設定し、ビルド成果物やGitへ含めない。
- 無料サービスのスリープ、コールドスタート、停止、容量・リクエスト制限を利用者に周知する。
- 無料枠を超えた場合の料金発生・停止条件を確認し、予算上限や利用停止手段を決める。
- Spotifyを追加する段階ではOAuth callback URL、HTTPS、secret保管、Spotify側の開発モード制約も確認する。

## 6. バックアップ・復旧

- CSVエクスポートは初期リリースに含めない。DBのバックアップ/復旧は独立した運用手順として用意し、初期版で利用者が自分のデータをCSV取得できるとは想定しない。
- マネージドDBを使う場合、バックアップ自動化の有無、保持期間、復元時点、復元料金を契約前に確認する。
- 自前バックアップを行う場合、暗号化し、本番DBと異なる保存先に保管する。アクセス権は最小限にする。
- 初期運用頻度は日次、保持期間は直近30日を候補とし、記録頻度・損失許容時間・保存料金を見て公開前に確定する。
- バックアップを別環境へ復元するテストを定期的に行い、手順と結果を記録する。
- アカウント・全データ削除機能はないため、利用停止/アカウント停止の運用とデータ保持方針を公開前に決める。

## 7. 運用確認

- 起動状態とヘルスチェック、アプリのエラー率を確認できる手段を用意する。
- ログにはrequest ID、日時、処理結果等を記録し、パスワード、Cookie、招待token、身体測定値を記録しない。
- Java/Node/MySQLのセキュリティ更新を確認し、更新時は自動テストとマイグレーションを実行する。
- DB容量、無料枠、請求通知、バックアップ成功を定期確認する。
- 障害対応時にDBを直接手修正せず、バックアップ取得・原因調査・復旧の順で進める。

## 8. 公開前チェックリスト

- 無料枠・有料時料金、上限、停止条件を公式情報で確認済み。
- DBの永続化、バックアップ、復元手順をテスト済み。
- HTTPS、Cookie属性、CORS、DB非公開、Secret設定を確認済み。
- 利用者とAdminの権限、承認待ちの扱いを本番設定で確認済み。
- データ保持・プライバシー告知・障害連絡方法を合意済み。
